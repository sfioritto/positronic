# Modernization step 7: dependency hygiene

**Status:** shipped
**Shipped:** 2026-09-05
**Started:** 2026-09-05

## Goal

Seventh and last step of the modernization plan. Everything still majors behind after steps 1 to 6: `@types/node`, zod, jose, dotenv, chokidar, yargs, eventsource, `@cloudflare/workers-types`; the packages that Node and workerd made redundant (uuid, node-fetch, nodemon); and the React packaging points carried from step 5. Each bump is its own commit so a regression bisects to one dependency.

## Log

### 2026-09-05 — the mechanical bumps

**Stale lockfiles.** `packages/cli`, `packages/cloudflare`, and `packages/core` each still had a `package-lock.json` from before the workspace setup (last touched 2025-07-26). npm ignores them in a workspace and they still pinned things like workers-types 4.20250406. Removed.

**`@types/node` 26.** Root pinned 20, spec 20, cloudflare 22. The first cut said 24 to match the Node on the laptop; Sean asked why not 26, since Node 26 is out (26.8.1 today, LTS next month) and is what a project started today would pick, and the laptop is not the constraint. So Node 26 went in through nvm (it ships npm 11.19, so npm 12 was installed on top of it, same as on 24), the gate ran green on it, and the types say 26 everywhere. One thing broke on the way: the cloudflare test-project's `vitest.config.ts` passed a `URL` to `fileURLToPath`, and in that project the global `URL` is the workerd one from `worker-configuration.d.ts` while `fileURLToPath` from `node:url` wants Node's, whose `searchParams.entries()` returns a disposable iterator under `@types/node` 24 and later. The two `URL` types had been compatible by accident. The config now builds its paths with `dirname` and `join` on strings, which is what it wanted anyway. `@types/node` 26 also stops exporting `JsonWebKey` from `crypto`; the CLI's SSH key utils name it as `webcrypto.JsonWebKey`. That one surfaced only because the gate output was read line by line: `npm run dev` ends in `|| terminal-notifier`, so it exits 0 when the build fails. Nothing declares `engines`; the effective floor after this step is Node 20.19 (yargs 18, chokidar 5), and the types are ahead of it, so a 26-only API would typecheck and fail on older Node. That is the trade Sean chose.

**uuid.** Core pinned 11 and cloudflare 9, both for `v4()`. Node 24 and workerd both have `crypto.randomUUID()` as a global, so the five call sites use it and both packages drop uuid and `@types/uuid`.

**node-fetch.** Only `packages/cli/tests/helpers.test.ts` imported it, for `Response`. Node 18+ has the global. Dropped.

**jose 6, dotenv 17, eventsource 5.** No source changes. jose 6 drops the `KeyLike` type for `CryptoKey`; nothing here named it. dotenv 17 logs a tip from `config()`, and the codebase only calls `parse()`. eventsource 5 keeps the `{ fetch }` init option the CLI passes for authenticated streams. The test-project has its own lockfile and jose pin, updated with it.

**chokidar 5.** This one changed API. chokidar 4 removed glob support and 5 is ESM-only, so the server command's watch list of `brains/**/*.{ts,tsx}`, `resources/**/*`, and `.env` had to become directories plus a filter. Dotfiles and `node_modules` are dropped by an `ignored` function that looks at path segments relative to the project root (chokidar 3's `/(^|[/\\])\../` regex would have matched a project living under `.test-cache`, which every CLI test project does). The `.tsx?` filter for brains lives in the event handler rather than in `ignored`, because chokidar calls `ignored` without stats for a path it has not yet stat'd and the extension check needs to know it is a file. The three copy-pasted `add`/`change`/`unlink` handlers collapsed into one that takes the event name.

The old regex also matched `<root>/.env` itself, so `.env` changes never reached `handleEnvChange` under chokidar 3; the new `ignored` exempts that path and env watching now works. There is no test for it (it would be a timing test around `awaitWriteFinish`), so it is called out here instead.

**The probe that validated the wrong chokidar.** The first scratch probes imported `node_modules/chokidar` from the root, which was chokidar 3.6 hoisted from nodemon; only after nodemon was removed did the probe resolve chokidar 5 from `packages/cli/node_modules`, and the results changed. Against chokidar 5 a burst of nine files written in the same tick loses one or two events, with or without an `ignored` matcher (chokidar 4 dropped fsevents, so macOS is on `fs.watch` now). With 300 ms between writes every expected event arrives, and the regex form of `ignored` that a reviewer proposed drops `.env` entirely. The burst loss is tolerable because every handler is a whole-directory operation: a brain event regenerates the manifest, a resource event resyncs all resources, so one surviving event from a burst does the same work as all of them.

**yargs 18, workers-types 5.** yargs 18 is ESM-only and needs Node 20.19+; the CLI is ESM and `@types/yargs` 17 still types it (yargs ships no types). workers-types 5 is what the test-project's `wrangler types` output already tracked; root, cloudflare, and the template's `.positronic/package.json` now agree.

**nodemon.** Gone, with `dev:watch`. `build:watch` is now `tsc --build --watch` over the eight package projects, which works because every package tsconfig extends the composite root. `npm run test:watch` was already Vitest's watch mode. `dev` keeps its terminal-notifier wrapper; the watch script lost its notifier, which is fine because tsc's watch output is the notification.

**`npm test -- <file>` was broken.** Vitest 4's `--silent` consumes the next positional, so `vitest run --silent packages/x.test.ts` fails with "Unexpected value --silent=packages/x.test.ts". The scripts now say `--silent=true`. Not a step 7 item, but the documented single-file command did not work and it is one line.

### 2026-09-05 — React packaging

`react` is now a peer dependency of gen-ui-components (`^19.2.0`), since its `dist` imports `react/jsx-runtime` at runtime. `@types/react` is a peer of core, since core's published declarations import `ComponentType` and React's `JSX` namespace; it started as an optional peer, but the first review pass pointed out that an optional peer is not installed and leaves a consumer with declaration files that only `skipLibCheck` hides, so it is a required peer. The template keeps its own `@types/react` line: npm 7+ installs required peers, but that could not be verified with the scratch-scaffolded project (its `file:` links do not install the target's peers) and pnpm and yarn differ, so the second review pass argued for keeping the one line. Root `overrides` for react, ink, and `@types/react` are not added; `npm ls` shows one copy of each and step 5 left the same verdict.

**The generated-page component bundle is broken in a fresh project, and this step does not fix it.** Scaffolding a project into the scratchpad (with `file:` links to the local packages), installing, and running `build:components` after pointing `bundle.ts` at `src/components` (the dev server creates the `.positronic/components` symlink at startup, so the standalone script only works after a dev server run) produces a 147 KB IIFE with twelve bare `require("react/jsx-runtime")` calls. esbuild's `external: ['react']` also externalises `react/jsx-runtime`, and an IIFE has no `require`. gen-ui-components has compiled with `jsx: react-jsx` since the package was added, so the bundle has imported the runtime since then; only components compiled in the project with the `React.createElement` factory work against the UMD React 18 globals. Fixing it means deciding the page runtime: either an esbuild alias that shims `react` and `react/jsx-runtime` onto `window.React`, or React 19 as ESM through an import map, which would also retire the React 18 UMD pin in `generate-page-html.ts`. Both touch the template config, the dev server's inline esbuild command, and the production deploy path, and both need a browser to verify. Recorded under Leftovers.

### 2026-09-05 — zod 4

`ai` 6 accepts zod 3.25 or 4.1+, so nothing external held zod back. Every package now says `^4.5.4`. Core, cloudflare, client-vercel, gen-ui-components, and mem0 declare it as a peer with a dev copy (the last three had it as a plain dependency, which is exactly how a project ends up with two zod copies and failing `instanceof` checks); the template has it in both its package.json files.

**`zod-to-json-schema` is gone.** It only supports zod 3. zod 4 ships `z.toJSONSchema`, used in two places through one `toJsonSchema` helper in cloudflare (`io: 'input'`, `unrepresentable: 'any'`), so the decision lives once: the token estimator, where the schemas describe tool input and a `z.date()` should degrade to `{}` instead of throwing (the first version left the estimator on the output side, which turns a `.transform()` field into `{}` and undercounts), and `GET /brains/:identifier`'s `options`, which describes what a caller sends. The output is draft 2020-12 instead of draft-07; nothing parses it. Cloudflare now declares zod as a peer, which it had been importing through zod-to-json-schema's dependency.

**What zod 4 renamed.** `AnyZodObject` and `ZodTypeDef` are gone; `ZodSchema` and `ZodTypeAny` survive as aliases. `z.record` needs a key schema, so the three `z.record(z.unknown())` sites say `z.record(z.string(), z.unknown())`. `ZodEnum`'s parameter is an entries object, so `FormPrimitive` says `z.ZodEnum<Record<string, string>>` and the enum values come from `.options` instead of `_def.values`. `.description` is a getter instead of `_def.description`. `ZodDefault` has `.unwrap()`. `unwrap()` and `.element` return the core `$ZodType`, so the walkers in `generate-page.ts`, `ui/types.ts`, and `schema-extractor.ts` take `z.core.$ZodType` and narrow with `instanceof` as before.

**The cross-bundle unwrap.** `parse-form-data.ts` inspects schemas by name rather than `instanceof` because brain bundles carry their own zod. zod 3 exposed `_def.typeName` (`ZodOptional`, `ZodEffects`); zod 4 exposes `_zod.def.type` (`optional`, `pipe`), and `.transform()` is a pipe with `_zod.def.in` rather than an effect with `_def.schema`. The walker now unwraps `optional`, `nullable`, `default`, `prefault`, `catch`, `readonly`, and `nonoptional` through `innerType`, and checks for `array`. A pipe needs a look at both sides: `.transform()` is `schema -> transform` (follow `in`) while `z.preprocess()` is `transform -> schema` (follow `out`); the first version followed `in` unconditionally and would have skipped array coercion for a preprocessed field, which the reviewer caught.

**Where `any` used to hide a constraint.** zod 3's `ZodType` defaulted its output to `any`; zod 4 defaults to `unknown`. Three generic constraints leaned on the old default. `withOptions<TSchema extends z.ZodSchema>` returns `Brain<z.infer<TSchema>>`, which must extend `JsonObject`; `StoreSchema` and `PerUserField` feed `Store<T extends Record<string, JsonValue | undefined>>`. The first version tightened them to `z.ZodType<JsonObject>` and `z.ZodType<JsonValue | undefined>`, which is what the store and options actually hold, but the reviewer pointed out that it rejects `z.date()` and friends that compiled before, and that is a contract change for a dependency bump; they now say `z.ZodType<any>`, which is what zod 3's `ZodSchema` meant. `generateObject<T extends z.AnyZodObject>` returned `object: z.infer<T>`; the test client's mock is a `vi.fn` whose erased signature has to be assignable back to the generic method, which only works when the constraint's output is `any`. Under zod 4 only `z.ZodType<any>` infers `any` (`ZodObject`, `ZodObject<any>`, `ZodObject<any, any>`, `ZodObject<ZodRawShape>`, and `ZodTypeAny` all give `Record<string, unknown>` or `unknown`; checked with a probe file and confirmed by the failing build with bare `ZodObject`), so the interface, the vercel client, and the test client all say `z.ZodType<any>`. The alternative was a cast in the test helper.

**`z.string().email()`** is deprecated in favour of `z.email()` but still works; the one test and the docs that use it are left alone.

### 2026-09-05 — review loop, pass 1

Taken: the `z.preprocess` unwrap (a real regression), `io: 'input'` in the token estimator, `z.ZodType<any>` instead of the tightened `JsonObject` and `JsonValue` bounds on `withOptions` and the store types, zod as a peer of client-vercel, gen-ui-components, and mem0, `@types/react` as a required peer of core with the template line removed, and a shorter `ignored` (one expression, splits on either separator since chokidar normalises to forward slashes). ### 2026-09-05 — review loop, pass 2

Taken: the template's `@types/react` line stays (see React packaging), mem0's empty `dependencies` key goes, and the three copies of the `toJSONSchema` options became `packages/cloudflare/src/json-schema.ts`. Declined: a guard in the token estimator for schemas from a zod 3 bundle (`z.toJSONSchema` reads `_zod.def` and throws on a zod 3 instance; zod-to-json-schema threw on foreign objects too, and the new peer range makes a zod 3 project fail at install rather than at request time, which is what a major bump of a peer is for); a `tsconfig.build.json` so `build:watch` can be `tsc --build --watch` with no list (a second hand-maintained list, one file more); `unknown` instead of `z.core.$ZodType` in the walker signatures (`z.core` is a documented zod 4 export, and the walkers are on the leftover list anyway); `engines` on cli and core (the plan chose no Node floor for the template; that is a policy decision, not hygiene); and a changeset for `.env` watching turning on (no step of this plan has added changesets; flagged in the report instead). ## Learnings

- Root `tsc --noEmit` does not check package sources. Files owned by a referenced project are excluded from the root program, so `npm run typecheck` covers tests, configs, and mem0; package `src` errors only appear in `npm run build:workspaces`. The zod bump had 30 root errors and then 3 more that only the build found.
- `git rm` of a nested lockfile in a workspace changes nothing about resolution; npm had been ignoring them.
- chokidar's `ignored` callback runs before the path is stat'd for new files, so `stats` is undefined on the call that decides whether an `add` fires. Filters that need to know file-versus-directory belong in the handler.
- `npm run dev` exits 0 on failure: the trailing `|| terminal-notifier` makes the notifier's exit code the script's. Read the `Test Files` and `error TS` lines, or run `build:workspaces && test:all && lint` directly when the exit code matters.
- A probe is only as good as its import path. `node_modules/chokidar` at the root was nodemon's chokidar 3 until nodemon left; the CLI's chokidar 5 lives in `packages/cli/node_modules`. Check `npm ls` before trusting a probe against a package that exists at two versions.
- chokidar 5 on macOS (no fsevents) can drop an event from a same-tick burst of writes. Handlers that regenerate a whole directory are immune; per-file handlers would not be.
- Vitest 4 parses `--silent <positional>` as `--silent=<positional>`; the value form is required when a file argument follows.
- Only `z.ZodType<any>` infers `any` in zod 4; every object-shaped `any` gives `Record<string, unknown>`.
- `z.toJSONSchema` reads `_zod.def`, not `instanceof`, so it works on schemas from a brain bundle's own zod copy, which `zod-to-json-schema` also did but by walking `_def`.
- Workers-types `URL` and Node's `URL` stopped being interchangeable with `@types/node` 24+'s disposable iterators; in a project with both globals, pass strings to `node:url` and `node:path`.

## Dead ends

- Adding `esnext.disposable` to the test-project's `lib` to make the two `URL` types compatible. The workerd `URL` still lacks the iterator members; the fix is not to mix them.
- Putting the brains `.tsx?` filter in chokidar's `ignored`. The probe showed `notes.md` getting through because `stats` is undefined on the first call.

## Leftovers

- The four `instanceof` schema walkers (`generate-page.ts`, `ui/types.ts`, `schema-extractor.ts`) could use `parse-form-data.ts`'s `_zod.def.type` walker, which is the one that survives a second zod copy in a brain bundle. Net deletion of about fifty lines and the `z.core.$ZodType` parameter types.
- The component bundle for generated pages has bare `require("react/jsx-runtime")` calls in a fresh project (see the React packaging entry). Page runtime decision: shim `react` onto `window.React` in the esbuild config, or React 19 ESM via import map and retire the UMD 18 pin. Needs a browser check.
- `npm run build:components` in a project only works after the dev server has created the `.positronic/components` symlink; `bundle.ts` imports `./components/index.js`.
- The template's `tests/example.test.ts` still fails when scaffolded (recorded in the plan since step 2).
- `.email()` in the docs and one test is the deprecated spelling; `z.email()` is the zod 4 form.
